# Architecture

## Build layout: one tree, two Minecraft versions (Stonecutter)

```
src/main/                  all code + shared assets, shown as the active version (1.21.1)
src/versioned/<mc>/        mod metadata and data files that differ per version
build.forge.gradle.kts     1.20.1 target: Forge 47, ModDevGradle legacy, Java 17
build.neoforge.gradle.kts  1.21.1 target: NeoForge 21.1, ModDevGradle, Java 21
versions/<target>/build/   per-target outputs (Stonecutter generates each target's source view here)
```

**Why Stonecutter over separate branches?** Control Engineering keeps 1.20.1 and 1.21.1 as long-lived branches; they've drifted by ~4,400 lines and its 1.21.1 port is unfinished. Stonecutter keeps one tree and marks only the differences with comments, so every fix lands in both builds at once.

**Where the differences live.** Create's APIs used here are identical on both versions, so the Create binding needs no branching. Vanilla differences (item-stack serialization, item custom data, dye colours, reach checks, `ResourceLocation`) go through `util/McCompat`; client rendering differences through `client/ClientCompat`. Loader differences (entry point, config, networking, client events, game-test annotations) are `//? if neoforge {` / `else` blocks in the handful of files that touch the loader; networking sits behind `network/CCNetwork`.

### Rules

1. Shared code must compile at Java 17 — the 1.20.1 build enforces this.
2. Shared code may only use Create APIs present in 6.0.8 — the 1.20.1 build compiles against 6.0.8, so it enforces this too.
3. Every direct Create API call stays behind a small internal interface (see frequency binding below), so a future Fabric target could bind it differently.
4. Registration uses Registrate (same library Create uses), so blocks/items inherit Create-style conveniences (lang merging, creative tabs).
5. Unit tests run on the 1.21.1 target inside FML (`gradlew :1.21.1-neoforge:test`); game tests run on both targets.

## Data model

```
PanelBlockEntity                – one console: ConsoleShape (angle, front height), ConsoleCasing, PanelLayout
 └─ PanelLayout                 – components on the 16×16 px face (design area 1..15 px); capped by config
     └─ PanelElement (abstract) – UUID id, float px position on a 0.5 px grid, FrequencyPair; size fixed by type (labels, bar meters and readouts set their own width or length)
         ├─ transmitters        – ButtonElement (button, large_button; pulseTicks), LatchingButtonElement,
         │                        SwitchElement, CoveredSwitchElement (guard open/closed + lever on/off),
         │                        AnalogElement → KnobElement, SliderElement (value 0-15)
         ├─ receivers           – ReceiverElement → LampElement (lamp, large_lamp), NeedleMeterElement,
         │                        BarMeterElement, NixieElement
         ├─ readouts            – ReadoutElement (line per row, size) → NixieStripElement (tubes),
         │                        DisplayBoardElement (two rows, width)
         └─ passive             – LabelElement (text, colour, scale, alignment, width, wrap + line count)
```

- Component types live in a string-keyed registry (`PanelElementType`, populated by `PanelElements`), each with a footprint and height (labels and bar meters override the width per element); unknown types are skipped on load with a warning. Layouts saved by v1 (cell grid, `Version` < 2) are dropped rather than misplaced.
- `FrequencyPair` = two item stacks (either optional, normalized to count 1), Create's frequency metaphor.
- Persistent state = design + latching component state; received strengths are runtime-only and resync from the link network via a `Runtime` list piggybacked on the update tag.
- Display Link text belongs to the console, by line number (`PanelBlockEntity.displayLine`), not to readouts, so readouts can mirror a line and re-pointing one takes effect at once. `ConsoleDisplayTarget` (registered in Create's display target registry and bound to the block in common setup) writes it: Link line 0 is console line 1, and the console offers lines up to the highest a readout shows. Like received strengths it is runtime-only, riding the update tag as component JSON so clients translate it; it is never saved, so blueprints and dropped consoles carry no old readings, and links resend it within seconds of a load.
- Server-authoritative: designer edits arrive as NBT ops (`PanelEditOps`: add, move, delete, set_frequency, set_option, adjust, set_shape) and `markLayoutChanged()` persists and pushes the whole console to clients.
- Costs: `ComponentCosts` maps each type to cost lines, each an item id or an `#item tag` (an unknown item id costs nothing). `CostPayer` charges the player's inventory when a part is mounted and returns the exact stacks taken, which the element keeps (`PanelElement.paid()`, saved as `Paid`) and refunds on removal; creative pays nothing, so creative parts refund nothing. Blueprint pastes go through `ComponentCosts.settle`, which reuses the old parts' paid items, charges the shortfall and refunds the rest. `ComponentCosts.totalOf` adds a design up by item, `shortfall` is what a paste over a given console would still charge (it changes nothing), and `held`/`lacking` count the stacks a player pays from. `MaterialList` turns cost lines into text coloured by what the player holds (red none, yellow some, green all; green without counts in creative); the palette tooltips, the blueprint tooltip and the blueprint designer's list all use it, so they count alike. The palette rebuilds its tooltips when `MaterialList.signature` changes.
- Unit tests in `src/test` run inside FML on the 1.21.1 target: `gradlew :1.21.1-neoforge:test`.

## Frequency binding (Phase 4, implemented — verified against Create 6.0.10 source)

We do **not** invent a signal system; we ride Create's Redstone Link network:

- Create's model (from `RedstoneLinkNetworkHandler` source): per-`LevelAccessor` map of `Couple<Frequency>` → set of `IRedstoneLinkable`; `Frequency.of(ItemStack)` keys by item + dyed color; strongest live in-range transmitter wins (`updateNetworkOf`); range is the `linkRange` server config (default 256).
- Common seam ([link/LinkPort.java](src/main/java/dev/mccastle91/createcontrolling/link/LinkPort.java), [link/LinkPlatform.java](src/main/java/dev/mccastle91/createcontrolling/link/LinkPlatform.java)): `LinkPlatform.createPort(level, pos, frequency, listening, transmittedStrength, receivedCallback, alive)` returns a `LinkPort` (`notifyStrengthChanged()` / `positionChanged()` / `remove()`). `pos` is a supplier, asked whenever range is measured, because a console on a contraption moves. No Create types cross this seam.
- Create binding ([CreateLinkPlatform.java](src/main/java/dev/mccastle91/createcontrolling/compat/create/CreateLinkPlatform.java)): one `IRedstoneLinkable` per panel *element* (not `LinkBehaviour`, which assumes one link per BlockEntity), registered with `Create.REDSTONE_LINK_NETWORK_HANDLER`, mirroring `LinkBehaviour`'s lifecycle: add on port create, remove on unload/delete/re-key, `updateNetworkOf` on value change. Fresh receivers self-compute their initial strength (the handler's push loop excludes the actor itself).
- Lifecycle hooks: `onLoad`/`onChunkUnloaded` are NeoForge patches, on NeoForge and Forge alike, so `CreatePanelBlockEntity` subclasses the plain BE to call rebuild/unload (it also supplies the body model's data and the goggles overlay, which is switched off pending a redesign); the common BE also lazily initializes ports on first server tick as a fallback and removes them in `setRemoved`.
- Designer frequency slots: slot 1 red, slot 2 blue — the two marker colours on Create's `redstone_bridge` texture (the first-frequency pad uses the red one). With JEI present, [compat/jei](src/main/java/dev/mccastle91/createcontrolling/compat/jei/) registers the designer as a plain-screen GUI (so JEI's list shows beside it; while the frequency chooser is open the designer hides and reports only the chooser's bounds, so the list fits at any GUI scale) and a ghost-ingredient handler whose only targets are the two frequency slots (the chooser's while it is open), dropping a dragged item through the same `set_frequency` op. JEI is an optional, client-side dependency compiled against its API only; nothing outside `compat/jei` references it, and its `IGuiProperties` method names differ per version (a Stonecutter branch).
- Component semantics: buttons pulse 15 for `pulseTicks` (server-ticked countdown), latching buttons and switches latch 0/15, the covered (guarded) switch sends 15 while its lever is on, knobs and sliders hold 0–15, optionally limited to a narrower range (`AnalogElement.min`/`max`: every way of setting the value clamps to it, the handle keeps its place on the full scale, and the renderer marks the stops); receivers take pushes into transient state synced to clients.

### Computers (optional CC: Tweaked peripheral)

- The common block entity carries a small automation surface with no CC: Tweaked types in it: `signalOf(element)`, `setSignal(id, strength)`, `clearDrivenSignals()`, the console's `name()`, and a static `SignalListener` registry (`addSignalListener` / `removeSignalListener`; listeners get the console, the element and the strength, server side only). `setSignal` on a control calls the element's `operate(strength)` hook (the programmatic twin of `click`), then goes through the same change path as a player's click. On a linked receiver, it opens a second, transmit-only `LinkPort` on that element's frequency ("drive port") whose strength the caller sets. The lamp then lights the ordinary way, through its own listening port, and so does every other link on that frequency. On an **unlinked** receiver, nothing joins the network: the strength goes straight into the element's received strength. Driven strengths are never saved. They follow the component through `rebuildLinkPorts`, and a drive port announces 0 before it leaves the network. `clearDrivenSignals` also darkens unlinked receivers. A receiver that loses its frequency in `rebuildLinkPorts` is reset to 0, so it never keeps a stale network value that only a computer could now overwrite.
- Console names (`TAG_NAME`, at most 32 printable characters, formatting codes stripped) are saved and synced with the block entity, set by the designer's `set_name` edit op, and not copied by blueprints (they carry the layout only).
- `PanelBlock.joinedConsoles(level, pos, max)` walks the `CONNECT_N/S/W/E` block-state flags breadth-first. They are symmetric, so any member finds the same group. It only looks into loaded chunks.
- [compat/computercraft](src/main/java/dev/mccastle91/createcontrolling/compat/computercraft/) wraps that as `ConsolePeripheral` (`control_console`: `getConsoles`, `getComponents`, `getValue`, `setValue`, `setFrequency`, all `mainThread`; `console_signal` events). One peripheral per console, kept in the block entity's `integrationData` (keyed by class) so computers on several sides share it. Each peripheral reaches its console's joined group, up to `ConsoleGroup.MAX_CONSOLES`. Methods take an optional trailing console selector: nil, a name, or an `x`/`y`/`z` table. `ConsoleGroup` holds the group, selector, component-numbering and frequency-parsing rules, with no CC: Tweaked types, so game tests cover it without the mod. Signal changes reach computers through one static listener: it checks the peripherals that have computers attached (`ACTIVE`) and queues the event on those whose console is in the changed console's group. When the last computer on a group detaches, every console in the group has its driven signals cleared, on the server thread.
- Registration: NeoForge 1.21.1 registers the block entity for `PeripheralCapability` in `RegisterCapabilitiesEvent`; Forge 1.20.1 uses `ForgeComputerCraftAPI.registerPeripheralProvider`. `CreateControllingMod` only touches `ComputerCraftCompat` behind `ModList.isLoaded("computercraft")`, and nothing outside the package refers to CC: Tweaked classes. It is compiled against the API jars only; the full mod is on the dev runtime classpath (like JEI) so `runClient` has computers to test with.
- Checked: game tests cover the automation surface on both versions. A driven lamp frequency reaches the lamp, a real Create receiver and the listener, and drops to 0 when released. A knob is operated to an exact value. An unlinked lamp and switch are set with no frequency, and the lamp goes dark when released and when unlinked. Two joined consoles form one group while a console standing apart does not, and consoles are selected by cleaned name and by position, refusing unknown, shared and out-of-group selectors. Frequencies parse from item ids, refusing unknown items and air. The multi-console peripheral itself (events across the group, `setFrequency` from Lua) was exercised from an in-game computer on the 1.21.1 dev client with the programs in `cc-tests/` (2026-11-18), with no errors in the log. It has not yet been tried in-game on 1.20.1. With CC: Tweaked loaded, the peripheral was found through NeoForge's capability lookup and its three methods exercised once by a throwaway test. Both versions also start and pass with CC: Tweaked absent. Not yet done: a Lua program on an in-game computer, and the Forge 1.20.1 provider lookup from a real computer.

### Cables (optional Drive-By-Sable endpoints, NeoForge 1.21.1 only)

- Drive-By-Sable (modid `drivebysable`) finds per-part endpoints by three interfaces on the **block**: `MultiChannelCableSource`, `ModuleSinkTarget`, `SubTargetCableEndpoint`. It adds them to Dashpanels by mixin; here `CableConsole` (in [compat/drivebysable](src/main/java/dev/mccastle91/createcontrolling/compat/drivebysable/)) implements all three with default methods, and `CCContent` registers `CableConsoleBlock` / `CableCopycatConsoleBlock` in place of the ordinary console blocks when the mod is loaded. Same registry ids and block entity, so worlds don't care which is in use. Those classes, and `DriveBySableCompat`, are only touched behind `ModList.isLoaded("drivebysable")`: loading them without the mod would fail on the missing interfaces. Every file in the package but `CableChannels` is wrapped in `//? if neoforge {`.
- A part is one sub target with one channel, both named by `CableChannels`: the part's English name plus the first 4 hex digits of its id (8 if two parts of a kind clash). Names are derived from the layout on both sides, never stored by us, and never change while the part exists; Drive-By-Sable stores connections by them.
- The common block entity gained three things with no Drive-By-Sable types in them: `setWiredSignal(id, strength)` and `PanelElement.receiveWired` (a receiver shows the stronger of its frequency's signal and the wired one; the wired one is runtime-only), a static `LayoutListener` fired at the end of `rebuildLinkPorts` (load and every layout change), and `integrationData` keyed by class so several integrations can each keep an object per console.
- `ConsoleCables` does the work. Controls push their value with `CableNetworkManager.trySetSignalAt` from the `SignalListener`. Drive-By-Sable delivers to receivers through `cable$applySinkSignal`. On a `LayoutListener` call the console is queued and brought in step on the next `ServerTickEvent.Post`, not at once: the listener also fires from `onLoad`, during chunk loading, when pushing a signal into other blocks is not safe. The sync drops the cables of parts that this same block entity knew a moment ago and that are now gone, re-sends every control's value and re-reads every receiver's signal (`getModuleSinkSignals`). It never drops anything on the strength of a part merely being absent: a console that has just been placed, loaded or moved onto a Sable vehicle can be seen with an empty layout before its data arrives, while Drive-By-Sable has already carried its connections over.
- Aiming (`cable$pickSubTarget`) runs `ConsolePicker` along the ray from the player's eye through the point their crosshair rests on (`player.pick`), the way `PanelBlock#interact` reads a click. Sable's ray cast gives that point in the console's own space on a vehicle. The outline is the part's footprint and height through `PanelFaceGeometry`.
- Clicks: Drive-By-Sable cancels `RightClickBlock` on the client for its Cable and Cable Cutter, so the console's own click never runs. The one thing ahead of that event is `AnalogDrag` (hold-and-drag on knobs and sliders, on the use key itself), so it and the sneak-scroll nudge stand down while either tool is in the main hand (`AnalogDrag.holdsCableTool`, by item id).
- Build: compiled against the mod jar from Modrinth's Maven (`maven.modrinth:drive-by-sable`), since it publishes no API artifact. It, Sable and Create Aeronautics join the dev runtime only with `-Pcables`. Aeronautics is there for the Simulated it bundles: Drive-By-Sable lists Simulated as optional, but its client crashes at load without it (its Ponder plugin).
- Checked: `CableGameTests` (they pass at once without the mod) ran with Drive-By-Sable r2.1.0 and Sable 2.0.6 loaded: both console blocks carry the interfaces; an unlinked knob cabled to an unlinked lamp on another console and to a plain block face drives both to the exact value; the lamp's console replacing its part objects keeps cable and signal; deleting the knob drops its cables and darkens the lamp. `CableChannelsTest` covers naming and the stronger-signal rule. Both versions build and pass their game tests without the mod. Not checked: anything a player does with the Cable item in a client (aiming, the highlight, the drawn cable), and consoles cabled on a Sable vehicle, including through assembly.

### Contraptions (consoles on elevators, trains and everything else Create moves)

- **What Create does with a moved block.** On assembly the block and its saved data become plain data in the contraption (`Contraption.getBlocks()`), and the block entity is removed, which takes every part off the link network. Clients get that data once and build a block entity from it in a level of their own (`ClientContraption`), which is why the console is still drawn. A block gets a tick only as an actor (`MovementBehaviour`), and a click only through a `MovingInteractionBehaviour`; both are registered for the two console blocks in `CCContent.commonSetup`. All of it is the same in Create 6.0.8 and 6.0.10.
- **One console class, two homes** ([panel/ConsoleHost.java](src/main/java/dev/mccastle91/createcontrolling/panel/ConsoleHost.java)). `PanelBlockEntity` does five things at its own world position: syncs to clients, plays sounds, marks itself changed, joins the link network, and refreshes neighbours and light. With a `ConsoleHost` set it asks the host for the first four and skips the last, and it tells no signal or layout listener, since computers and cables know a console by its place in the world. So a console off the world runs the same part code as a placed one. Anything new that touches `level` at `worldPosition` in that class must go through `placeInWorld()` or check `host`.
- **Server** ([compat/create/contraption](src/main/java/dev/mccastle91/createcontrolling/compat/create/contraption/)). `MovingConsole` is the host: a console built from the contraption's data, kept in the actor's `MovementContext.temporaryData`, made on the actor's first tick and ticked from there (`ConsoleMovement`). Its position is the actor's current block position, and `visitNewPosition` has the link ports measure range again. Every saved change is written straight into the contraption's own copy of the data, so a world save or a disassembly carries the console as it is. It closes (ports leave the network) on `stopMoving`, which Create also calls on a contraption that carries on, so the next tick simply starts a new one, and on `EntityLeaveLevelEvent`, because a contraption unloaded with its chunk is never told to stop. For one tick at assembly the console is on neither network entry: the placed console has left and the moving one has not ticked yet.
- **Clicks.** Create ray-traces the contraption on the client and asks the block's interaction whether the click did anything, without saying where on the block it landed. `client/ContraptionConsoles.click` moves the player's ray into the contraption's space (`toLocalVector`, at the frame's partial tick, then at 1 as Create's own ray uses), runs `ConsolePicker` on the client's block entity, and sends a `ContraptionClickPayload` naming the part, zone and spot. The client picks because the server's idea of where a moving cabin is lags the picture. `MovingConsole.click` checks reach (with 4 blocks of slack), the part and the zone, then calls the same `clickElement` a placed console's click ends in.
- **Shapes.** Create asks a contraption block for its shapes through `ContraptionWorld`, where a console has no block entity to read its real shape from, and for the click ray at a made-up position. `WrenchablePanelBlock` answers there with the whole block for the ray and the console's default shape for collision. Since the ray then stops at a console's block even where it only crossed air above a low console, a click that finds no part is passed on: `ContraptionConsoles.passOn` runs Create's ray again from where it leaves the block and hands the click to whatever it finds.
- **State to clients.** `ContraptionSyncPayload` carries the console's update tag to everyone tracking the contraption, at most once a tick; a player who starts tracking one is sent each of its consoles (`PlayerEvent.StartTracking`), since Create's spawn data holds them as they were at assembly. The client writes the tag into the contraption's data, which Create rebuilds its client block entities from, and into the block entity being drawn.
- **Left out for now:** the designer and every item that acts on a console (casing, dye, blueprint, clipboard) do nothing on a contraption; hold-and-drag and the part highlight need the world's hit result and have no contraption path yet; Display Links, computers and cables don't reach a moving console. A receiver left further than the link range behind a moving transmitter keeps its last value until something on its frequency changes, as Create's network only pushes to links in range.
- Checked: `ContraptionGameTests.consoleOnAnElevatorKeepsWorking` on both versions. A real elevator (pulley, creative motor, a cabin of one Redstone Contact with a wall console on it, an Elevator Contact) assembles with the console aboard; a click through `MovingConsole.click` switches a real Create receiver on; a real Create transmitter's 9 reaches the lamp on the elevator; taking the elevator apart puts the console back with its switch on, still sending, and switching it off then turns the receiver off, so nothing of the moving console is left on the network. Not checked, because no test has a client: how the console is drawn on a contraption, the click ray and the pass-on, the sync packet arriving, sounds, and every contraption type but the elevator.

### Verified by GameTests (`gradlew :1.21.1-neoforge:runGametest`, `gradlew :1.20.1-forge:runGametest`)

Real Create Redstone Link blocks + our panel in a live server: button pulse powers a Create receiver then expires; knob analog 11 arrives as exactly 11; a Create transmitter's analog 7 lights our lamp at exactly 7; a player's click ray on a 15° sloped console presses the button under it; real Display Links write through the target Create resolves for a console, filling lines, clearing lines a source stops filling, and stopping at a line another link owns. 4. Face-attached blocks need an in-test floor; don't rely on the structure template for support blocks.

## Console block

One block, `PanelBlock` (face-attached like a lever: floor, wall, ceiling × four facings), plus a block entity. Everything spatial derives from one mapping, `ConsoleOrientation`: model space is a floor console facing north (player standing south), and each of the 12 placements is a rotation of it. `PanelFaceGeometry` describes the sloped face in that space (origin at design (0, 0), `u` right, `v` down the design, outward normal), so the body mesh, the component renderer, the click ray (`ConsolePicker`), the voxel shapes (`ConsoleShapes`) and the highlight (`ConsoleOutline`, which draws the aimed component or the true wedge instead of the stepped selection shape) agree by construction. Where a casing has Create connected textures, the walls of joined consoles use them (`ConsoleMesh`).

- **Shape:** angle, front (hinge) height and which model edge is raised, stored on the block entity and normalised to what the placement allows (`ConsoleShape.forFace`): floor consoles rise away from the player; ceiling consoles hang their far edge down; wall consoles start flat and may raise either their top or their bottom edge. The ceiling's design frame is turned 180° from the floor's so the face reads upright from below, which puts its hinge at model z = 0 — so a ceiling slope is "reversed" in model space while looking the same as before in the world. A console item keeps its old shape, but a console placed on a wall always starts flat (`PanelBlock.setPlacedBy`). The wrench steps through the 0/15/30/45° presets (walls: top out, then bottom out, then flat), and sneak-wrenching is Create's default pick-up into the inventory; the designer sets any angle and, on walls, the raised edge.
- **Casing:** right-click with a Create casing (andesite, brass, copper, railway, industrial iron, weathered iron) to re-dress the console; the old casing comes back.
- **Copycat console:** a second block, `copycat_control_panel` (`compat/create/CopycatConsoleBlock`), sharing the block entity type and everything else. Its casing is fixed (`PanelBlock.fixedCasing()` → `ConsoleCasing.COPYCAT`: copycat-base body, zinc trim, zinc screens), so every consumer of the casing works unchanged; no item applies that casing and no other block may wear it. The block entity stores the copied `BlockState` (`Material`) and the item it was applied with (`MaterialItem`), like Create's copycats; only this block reads them. Which blocks are accepted is Create's rule, asked of its Copycat Step (`getAcceptedBlockState`, same signature in 6.0.8 and 6.0.10). Create crops the copied block's quads to a box, which can't follow a slope, so the body keeps its own mesh and borrows textures instead: `ConsoleMesh.Skin` gives, per world side, the sprite and tint index of each quad the copied block's model has there, and every casing-textured quad (walls, bottom, frame) is emitted once per layer with them; the sloped face counts as the block's top. The plate is untouched. The copied block may draw in other render layers than the console's solid one, so `ConsoleBakedModel` reports the union and builds one mesh per layer (the cache key carries material and layer). Plain models return the same quads whatever layer is asked for, so `layers` asks only for the layers the copied block draws in (otherwise glass is also drawn solid). A bare copycat console is skinned the same way with the copycat frame texture in the cut-out layer, so the frame's gaps are open as on Create's copycats. Because the body may be see-through, a skinned console's face has an underside quad (plate texture). A block colour handler passes tints through to the copied block.
  - **Texture mapping** (`SkinMapping`): a skinned quad's corners don't use the casing's texture layout. Each takes the texture px its position in the block has on that world side by vanilla's default (`defaultUv`), so the skin lies where it does on the real block and lines up across joined consoles; the sloped face reads as the block's top seen from above, and a low wall shows the lower part of the texture. Each `Layer` also carries the linear map from those px to atlas coordinates, solved from the copied block's own quad (`SkinMapping.of`), so whatever the model does with its texture carries over: a log on its side, mirrored or part-sprite UVs, connected-texture tiles. A quad covering under 12 px of the side is a detail and falls back to the whole sprite.
  - **Connected textures**: Create's (and any mod's that work through model data) are computed by the copied block's own model. `ConsoleBakedModel.getModelData` asks that model for its data at the console's position, through Create's `FilteredBlockAndTintGetter` showing only the console itself and the consoles it is joined to (`PanelBlock.joinedToward`, the same rule as the edge flags), and stores it as `WRAPPED_DATA`; the skin's quads are then fetched with it, already moved onto the right tile. `CopycatConsoleBlock.getAppearance` answers a console's query with the copied block, and any other block's with the console itself, so copies connect to each other and real blocks don't run their texture into a wedge. A mesh built with such data is not cached (the data is new on every chunk rebuild); a per-thread one-entry memo covers the per-side calls of one rebuild.
  - **Light**: the console gives off the copied block's light. On NeoForge the block reports the chunk's auxiliary light (`hasDynamicLightEmission`, `getAuxLightManager`), which the block entity sets on load and whenever the block changes (`updateMaterialLight`, both sides), as Create's copycats do; on Forge 1.20.1 the block asks the block entity's material and the block entity has the light engine recheck the position. A copied block with `emissiveRendering` (magma) has full brightness baked into its skin quads.
- **Connections:** the blockstate records which edges meet an identical neighbour (same block, placement, shape, casing and copied block; sloped consoles only join side by side). Joined edges lose their frame so a row of consoles reads as one surface. Changes to shape or casing refresh the 3×3×3 neighbourhood.
- **Drops** keep the design (block-entity data on the item, restored on placement).
- **Rendering:** see [docs/v2-design.md](docs/v2-design.md#rendering) — a bake-time `ConsoleBakedModel` for the body (chunk-lit, so it shades correctly at any angle) and a block-entity renderer for the 3D components.

## Interaction model

- **Play** (right-click): the player's eye ray, transformed into face space, is intersected with each component's 3D box; the nearest hit handles the click at the exact point. A click steps a knob or slider up one; a sneak-click steps it down one (`PanelElement.takesSneakClicks` lets it claim the sneak-click before the designer does). Sneak + scroll also nudges it by one.
- **Body quad corner order:** vanilla's smooth lighting shades a partial-face quad's corners by position in the list, not in space, so `ConsoleMesh` rotates each quad's corners to start where vanilla starts that face (`vanillaStart`). Without it every rotated console is shaded a quarter turn out, most visibly as dark lines on the 1 px strips between joined consoles.
- **Trim:** the metal trim of every part (bezels, housings, pivots, hinges, sockets) is one sprite the renderer looks up per console from `ConsoleCasing.trimTexture()`, so it follows the casing with nothing extra saved; the dial window uses the same lookup.
- **Sounds:** a part notes a `PartSound` when its state changes through a hand or automation (`click`, `scroll`, `operate`, a button's pulse ending) — never when a value is merely set or loaded — and `PanelBlockEntity` plays it once from the console's position (vanilla button, lever and trapdoor sounds). A player dragging a knob hears each step from their own client and is left out of the server's copy.
- **Click zones:** a part may offer the click ray several boxes (`PanelElement.pickBoxes`); `ConsolePicker` reports which was hit as the click's zone, and the highlight outlines that box. The guarded switch uses this once its guard is open — the switch underneath is one zone, the raised lid another — so the guard and the lever are clicked separately (sneak-click works the guard from anywhere). The lid stands above the part's normal height, so the block's selection shape covers every part up to `PanelElement.reach()`, whatever state it is in.
- **Hold-drag** (client, `AnalogDrag` + `AnalogDragScreen`): the use key on a knob or slider, not sneaking, is intercepted before it becomes a click and opens a screen for as long as the key is held. The screen exists to stop the camera turning; it turns mouse travel into steps (a fixed distance per value, with a click sound) and sends each as a `set_value` op, which moves the control without a layout resync (`PanelBlockEntity.setAnalogValue`). A release within a few ticks with no movement counts as a tap and steps up one. The client config `analogPopup` draws the control itself in a window (`AnalogDial`, the renderer's geometry from above) instead of nothing.
- **Clipboard** (`compat/create/ClipboardFrequencies`): Create's clipboard handler only serves its own SmartBlockEntity behaviours, so consoles have their own — right-click copies the aimed component's frequency, left-click pastes — reading and writing Create's internal clipboard layout (`Frequencies` → `First`/`Last`) so it interoperates with real Redstone Links. That layout is not public API; a gametest round-trips through a real link on both versions.
- **Label text** is measured only on the client (a server has no font): `client/LabelText` decides line breaks, the designer limits typing and sends the line count a label needs with each change, and the renderers clip to the footprint regardless.
- **Edit** (sneak + empty hand, not on a knob or slider): opens the Console Designer. Every change is sent as an edit op and the screen redraws from the synced block entity.
- **Screen look** (client): every screen takes its look from the console's casing through `CasingTheme` (one per casing) and its shapes from `ConsoleGui`, which draws Create's menu parts to any size — title bar, checkered body, grey footer, slots, fields, buttons, the angle slider — since Create's own windows are fixed-size pictures. Each shape is a small nine-cut texture in `textures/gui/console/` (corners as they are, edges and middle stretched, or repeated where the texture has a pattern; the borders are the `Cut` constants in `ConsoleGui`). A theme is a folder there holding its title bar and body tile, and may hold its own copy of any shared texture (`ConsoleStyle.texture` looks there first and caches the answer until the next reload). `tools/gui_textures.py` draws all of them in the colours the screens were filled with before 0.2.8, taken from Create's GUI textures. Colours a texture can't carry — text, the face's grid, the flat parts, and the fixed colours of the 3D parts — are `StyleColor` entries, which `ConsoleStyle` (a client reload listener) overrides from every pack's `console_style.json`, lowest pack first; a theme's title text and accent are overridden the same way. Nothing reads a colour constant directly any more: to add one, add a `StyleColor` and a row in `docs/resource-packs.md`. Create's sprites are used directly where they fit as they are (`AllGuiTextures.BUTTON*` and `PLAYER_INVENTORY`, `AllIcons` for the tick and bin; all present in 6.0.8). `ThemedButton` is a vanilla `Button` drawn that way, so lists of widgets, tooltips and narration are unchanged. The designer does not call `Screen.render`: it draws the dimmed world, the window, then its widgets, so the window sits between them (the background call differs per version, a Stonecutter branch). The face is the casing's and the plate's block-atlas sprites at face scale. `ConsolePreview` draws the console beside the window with the world's own baked model (join properties cleared, so it shows whole) and block entity renderer; it is skipped when the screen is under 80 px wider than the window, and switches itself off if drawing ever throws.
- **Labels that fit** (from GitHub issue #4, the French translation): `ConsoleGui.centeredFitted` draws a centred line no wider than the room it is given: as it is if it fits (so English is untouched), else scaled down to fit, never below `MIN_TEXT_SCALE` (0.6), and cut to an ellipsis past that. `ThemedButton` draws every text button's label with it, and the designer the text between a row's - and + buttons; the selection header had its own squeeze already (`drawFitted`). This was chosen over a "smaller text" option, which the author had offered on the issue: it needs no setting and shrinks only what doesn't fit.
- **Part sounds**: `PartSound.Kind` is one sound event each (`create_controlling:part.*`, registered in `CCContent`), which `sounds.json` points at vanilla's button, lever and trapdoor events, so the default sound is unchanged and a pack can replace any of them. `Kind.event()` falls back to the vanilla event where the registry has none (unit tests). The client option `partSounds` drops those events in `PlaySoundEvent`.
- **Add-on API** (`api`, `api.client`; guide in `docs/api.md`): `ConsoleApi.registerComponent` is `PanelElementType.register` with a namespaced id, `setCost` fills `ComponentCosts`. What the mod's own code used to decide by `instanceof` has a hook for parts it doesn't know: `PanelElement.options()`/`setOption` (four generic rows in the designer, tried first by `PanelEditOps.applyOption`), `describe` (CC `getComponents`), and on the client `ConsoleClientApi.registerRenderer`, which `PanelBlockEntityRenderer` and the designer's flat drawing ask before their own chains; a renderer that throws is logged once and skipped, and an add-on part with no renderer draws as a plain plate. The mod's own parts still go through the built-in chains and return no generic options. Translation keys use `PanelElementType.langId()` (colon to dot). The palette pages past 20 types. `ConsoleApiTest` takes a stand-in add-on part through registering, cost, edit ops, options and saving.
- **Face plate colour**: `PanelBlockEntity.plateColor` (a `DyeColor`, null for the standard plate; saved and synced as `Plate`, so it rides the dropped item like the casing; not part of the layout, so blueprints don't carry it). A dye on the console sets it (`PanelBlock.applyPlateDye`, before casings; one dye used, none if the colour is unchanged); gray is the standard plate, so gray dye clears it. There is no tinting at draw time: each dye has its own plate texture (`block/console_plate_<dye>.png`, drawn from the standard plate by `tools/plate_textures.py`), chosen by `ConsoleBakedModel.plateTexture` from the `PLATE_PROPERTY` model data, so the world, the designer's face and the console beside the designer all show it with no colour handler, and a resource pack can redraw any one of them. The console item's icon always shows the standard plate, as it always shows the default casing.
- **Blueprint** (`PanelBlueprintItem`): the item holds a `PanelLayout` in its custom data (`Layout`, plus `ElementCount` so the tooltip and icon need not parse it). A drawing owns no items: copying strips `Paid`, and drawn parts are never paid for.
  - Clicks: `use` (air, or a block that isn't a console) opens the designer on the item. On a console, an empty blueprint copies; one holding parts only reports what a paste would lack, and pastes on a sneak-click. A sneaking player's click skips the block, so `PanelBlock` handles the plain click and the item's `useOn` the sneak-click; both end in `useOnPanel`.
  - Designer on a blueprint: `PanelDesignerScreen(InteractionHand)`. The screen has no console (`panel()` is null) and reads the layout off the held stack every tick, since the server answers each edit with a new stack. Edits go out as `BlueprintEditPayload(hand, op)`, which the server applies with `PanelBlueprintItem.edit` to whatever blueprint is in that hand, with `CostPayer.FREE`. `PanelEditOps.applyToLayout` holds the edits that only touch a layout (add, move, delete, frequency, option), shared by consoles and blueprints; shape, name and the copied block stay in `apply`, and `clear` is the blueprint's own op. The screen leaves out the shape controls, the name and the 3D preview, wears `CasingTheme.BLUEPRINT`, and lists the drawing's materials while nothing is selected.
  - Icon: the item model overrides to `panel_blueprint_filled` on the `create_controlling:filled` item property, registered in client setup from the part count.
